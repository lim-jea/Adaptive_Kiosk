# 프론트엔드 기능 점검 정리

작성일: 2026-04-29  
기준 코드: `frontend/src/*`, `backend/docs/프론트엔드_API_링크_정리.md`

이 문서는 디자인 변경을 제외하고, 현재 프런트에서 구현되어 있거나 앞으로 기능 개발 시 주의해야 할 항목을 정리한 문서다.

## 1. 현재 프런트 기능 흐름 요약

현재 프런트는 아래 흐름으로 동작한다.

1. `/` LandingPage
   - `POST /api/v1/sessions`로 세션 생성
   - `session_uuid`를 React Context와 `sessionStorage`에 저장
   - 직접 연령대 선택 또는 카메라 인식으로 다음 화면 이동

2. `/camera` CameraPage
   - 브라우저 카메라 시작
   - 프레임 5장 캡처
   - `/analyzing`으로 프레임과 `sessionUuid` 전달

3. `/analyzing` AnalyzingPage
   - `POST /api/v1/face/analyze`
   - 분석 결과를 전역 세션 상태에 저장
   - `/result`로 이동

4. `/result` ResultPage
   - 분석 결과 확인
   - 주문 화면으로 이동

5. `/kiosk` KioskPage
   - `GET /api/v1/categories`, `GET /api/v1/menus`
   - 메뉴 상세 진입 시 `GET /api/v1/menus/{menu_name}`
   - 장바구니 로드: `GET /api/v1/carts/{session_uuid}`
   - 장바구니 변경 시 전체 교체: `PUT /api/v1/carts/{session_uuid}`
   - 추천 패널과 음성 주문 연동

6. `/payment` PaymentPage
   - 프런트 장바구니 기준으로 결제 요약 표시
   - 결제 수단 선택 후 2초 대기
   - `POST /api/v1/orders`로 주문 생성
   - `/complete`로 이동

7. `/complete` CompletionPage
   - `PATCH /api/v1/sessions/{session_uuid}`로 세션 종료
   - 30초 카운트다운 후 홈 이동
   - 홈 이동 시 Context와 `sessionStorage`의 세션 제거

## 2. 꼭 주의해야 할 기능 항목

### 2.1 API 주소와 키오스크 API Key

현재 프런트 API 기본값은 `frontend/src/utils/api.js`에서 `http://localhost:5000`이다.

필수 환경변수:

```env
VITE_API_URL=http://localhost:5000
VITE_KIOSK_API_KEY=키오스크_API_KEY
VITE_ENCRYPTION_ENABLED=false
```

주의:

- `POST /api/v1/sessions`는 `X-API-Key`가 필요하다.
- `VITE_KIOSK_API_KEY`가 비어 있으면 첫 세션 생성부터 실패한다.
- Docker도 백엔드를 `5000:5000`으로 열고 있으므로 프런트 개발 기준 URL은 `5000`으로 통일해야 한다.
- 관리자용 API는 Basic Auth가 필요하지만 현재 일반 키오스크 프런트에서는 직접 호출하지 않는다.

### 2.2 세션 생성과 복구

현재 세션은 LandingPage에서 만들고, `sessionStorage.session_uuid`에 저장한다.

주의:

- 새로고침하면 React Context의 `sessionUuid`, `cart`, `vision` 값은 초기화된다.
- 일부 화면은 `sessionStorage`에서 세션을 다시 읽지만, 모든 상태를 완전히 복구하지는 않는다.
- `/kiosk`, `/payment`, `/complete`에 직접 진입했을 때 세션/장바구니가 비어 있을 수 있다.

권장:

- 앱 시작 또는 주요 페이지 진입 시 `sessionStorage.session_uuid`가 있으면 Context로 복구하는 초기화 로직을 추가한다.
- `/payment`는 `state.cart.length === 0`이면 `/kiosk` 또는 `/`로 보내는 가드를 둔다.
- 세션 종료 후에는 서버 장바구니와 로컬 장바구니를 모두 정리하는 흐름을 명확히 둔다.

### 2.3 장바구니 동기화

현재 장바구니는 프런트 Context가 1차 상태이고, 서버에는 `PUT /api/v1/carts/{session_uuid}`로 전체 교체한다.

현재 처리:

- KioskPage 진입 시 서버 장바구니를 한 번 로드한다.
- 로컬 장바구니 변경을 감지해 서버에 전체 동기화한다.
- 결제 생성은 `POST /api/v1/orders`에서 서버 저장 장바구니 기준으로 진행한다.

가장 중요한 주의점:

- 결제 페이지로 이동한 직후 서버 동기화가 아직 끝나지 않았으면 주문이 이전 장바구니로 생성될 수 있다.
- `PUT /carts` 실패 시 UI에는 반영됐지만 서버에는 저장되지 않은 상태가 될 수 있다.
- PaymentPage는 서버 장바구니를 재검증하지 않고 로컬 장바구니로 표시한다.

권장:

- 결제 버튼 클릭 전에 마지막 `PUT /carts/{session_uuid}`가 성공했는지 보장한다.
- `/payment` 진입 시 `GET /carts/{session_uuid}`로 서버 장바구니를 다시 읽어 로컬 상태와 맞춘다.
- `PUT /carts` 실패 시 결제 버튼을 막거나 사용자에게 재시도 안내를 보여준다.
- 수량 제한은 프런트에서도 1~99 범위를 유지한다.
- 장바구니 항목 key는 `menuName + optionIds`인데, 서버 응답의 `line_id`와 로컬 생성 key가 항상 같은 규칙인지 계속 확인해야 한다.

### 2.4 가격 계산

현재 프런트는 `unitPrice * quantity`로 합계를 계산한다. 서버는 주문 생성 시 가격을 검증/재계산한다.

주의:

- 프런트 금액은 표시용으로 보고, 최종 주문 금액은 서버 응답의 `total_price`를 신뢰해야 한다.
- PaymentPage에서 주문 생성 후 CompletionPage로 넘기는 `totalPrice`는 주문 API 응답값이 아니라 프런트 계산값이다.
- 옵션 가격 변경, 품절, 메뉴 가격 변경이 서버에서 발생하면 프런트 표시 금액과 주문 금액이 달라질 수 있다.

권장:

- `POST /orders` 성공 후 `res.data.total_price`를 완료 화면에 넘긴다.
- `orderUuid`도 완료 화면에 넘겨 실제 주문번호로 표시한다.
- 결제 직전 서버 장바구니 조회 결과의 `total_price`를 기준으로 표시한다.

### 2.5 주문 생성 실패 처리

현재 PaymentPage는 주문 생성이 실패해도 완료 화면으로 이동한다.

주의:

- 실제 주문이 생성되지 않았는데 결제 완료처럼 보일 수 있다.
- `orderUuid`가 null인 완료 화면이 발생할 수 있다.

권장:

- `POST /api/v1/orders` 실패 시 완료 화면으로 이동하지 말고 결제 화면에 오류/재시도 버튼을 표시한다.
- 실패 로그는 남기되 사용자 흐름은 멈추는 것이 안전하다.
- 주문 생성 성공 후에만 세션 종료를 진행한다.

### 2.6 세션 종료와 타임아웃

현재 세션 종료는 CompletionPage 진입 시 `status=ended`, `end_reason=completed`로 PATCH한다.

현재 자동 타이머:

- 완료 화면에서 30초 카운트다운 후 홈으로 이동

주의:

- 사용자가 중간에 홈으로 돌아가거나 브라우저를 닫으면 세션이 `active`로 남을 수 있다.
- KioskPage/PaymentPage에는 무사용자 타임아웃이 없다.
- CompletionPage의 `handleGoHome`은 async인데 interval 안에서 호출되므로, 중복 호출 방지 플래그가 있으면 더 안전하다.

권장:

- 전체 주문 플로우에 무사용자 타이머를 둔다.
- 타임아웃 시 `PATCH /sessions/{session_uuid}`로 `status=abandoned`, `end_reason=timeout` 처리한다.
- 홈 버튼/뒤로가기/취소 버튼은 `cancelled` 또는 `abandoned` 정책을 정해서 서버에 반영한다.
- 완료 화면 자동 이동과 사용자의 홈 버튼 클릭이 동시에 발생하지 않게 `isNavigatingHome` 같은 guard를 둔다.

### 2.7 음성 주문 액션 처리

현재 음성 흐름은 `useVoiceOrder`에서 `/voice/start`, `/voice/messages`, `/voice/end`를 호출하고, KioskPage의 `handleVoiceAction`이 action을 UI에 반영한다.

주의:

- 음성 action이 장바구니를 바꾼 직후 서버 동기화는 KioskPage의 effect에 의존한다.
- `place_order` action이 오면 장바구니가 있으면 바로 `/payment`로 이동한다.
- 이때도 마지막 장바구니 동기화 성공이 보장되지 않을 수 있다.
- `cart_add` action에서 `fromRecommendation` 값이 빠져 있어 음성으로 추천 메뉴를 담은 경우 추천 유입 여부가 누락될 수 있다.

권장:

- 음성 `place_order` 처리 전에 장바구니 서버 동기화를 명시적으로 기다린다.
- action 처리 실패 시 사용자에게 음성/화면으로 다시 요청하도록 안내한다.
- `cart_add`, `cart_update`, `cart_remove` 후 로그와 서버 장바구니가 일관되도록 한다.
- `voice/end`는 화면 이탈, 결제 이동, 세션 종료 시점에 누락되지 않게 호출한다.

### 2.8 추천 기능

현재 추천 패널은 프로필 정보와 장바구니를 기반으로 추천 API를 호출한다.

현재 처리:

- 나이 숫자가 있으면 `POST /recommendations/suggest`
- 실패하면 `GET /recommendations/situation`으로 fallback
- 장바구니가 바뀔 때마다 추천을 다시 호출한다.

주의:

- `cartItems` 배열이 바뀔 때마다 API 호출이 발생하므로 장바구니 변경이 잦으면 호출이 많아진다.
- `gender`가 `unknown`이면 현재 로직상 기본적으로 `M`으로 보내는 흐름이 있다.
- 직접 연령대 선택값과 백엔드가 기대하는 `age_group` 코드가 어긋나면 추천 품질이 떨어질 수 있다.

권장:

- 추천 호출에 debounce 또는 간단한 캐싱을 둔다.
- `unknown` 성별일 때는 기본값 정책을 명확히 한다. 예: `M` 고정, 전체 인기 fallback, 성별 없는 추천 API 추가.
- 추천 메뉴 클릭으로 담은 경우 `fromRecommendation=true`가 주문까지 이어지는지 확인한다.

### 2.9 얼굴 분석과 카메라

현재 카메라 캡처는 5장을 200ms 간격으로 촬영하고 `/face/analyze`에 전달한다.

주의:

- `.env.example`에는 암호화 옵션이 있지만 백엔드는 현재 평문 Base64 프레임을 받는 구조다.
- 카메라 권한 실패, HTTPS가 아닌 환경, 카메라 장치 없음에 대한 fallback이 필요하다.
- 분석 실패 시 재시도/처음으로 이동은 있으나, 분석 없이 주문으로 진행하는 fallback이 있으면 현장 사용성이 좋아진다.

권장:

- `VITE_ENCRYPTION_ENABLED=false` 유지
- 카메라 실패 시 직접 연령대 선택으로 돌아가는 버튼을 명확히 제공
- 분석 API 실패 시 세션은 유지하고 일반 모드로 주문 진행 가능하게 한다.

### 2.10 로그 수집

현재 `useLogger`는 전역 버퍼에 이벤트를 쌓고, 20개 이상이거나 명시적 flush 시 `/logs/batch`로 보낸다.

주의:

- 세션 생성 전 landing 로그는 세션 없이 쌓였다가 세션 생성 후 flush된다.
- flush 실패 시 버퍼에 다시 넣는 구조는 좋지만, 브라우저 종료 시 남은 로그는 유실될 수 있다.
- 전역 `sharedSeq`는 새 세션에서도 계속 증가한다.

권장:

- `beforeunload` 또는 페이지 숨김 시점에 flush를 시도한다.
- 세션이 바뀌면 `sharedSeq` 초기화 여부를 정책으로 정한다.
- 중요 이벤트는 즉시 flush하거나 주문 생성 직전에 반드시 flush한다.

### 2.11 완료 화면의 부가 기능

현재 스탬프, 주차 등록, 주문번호는 프런트 시뮬레이션이다.

주의:

- 스탬프는 `sessionStorage.stamp_count` 기반이라 실제 회원/DB와 무관하다.
- 주문번호는 랜덤 3자리라 실제 `order_uuid`와 연결되지 않는다.
- 주차 등록은 실제 API 호출 없이 UI 상태만 바뀐다.

권장:

- 실제 운영 기능으로 쓸 예정이면 회원/스탬프/주차 API가 별도로 필요하다.
- 지금 단계에서는 "시연용 기능"으로 명시하거나 실제 API 연동 전까지 주문 완료의 핵심 정보와 분리한다.

## 3. 우선순위별 작업 제안

### 최우선

1. 주문 생성 실패 시 완료 화면 이동 금지
2. 결제 직전 서버 장바구니 동기화 보장
3. CompletionPage 표시 금액을 주문 API 응답값 기준으로 변경
4. `/payment` 직접 진입/새로고침 시 세션과 장바구니 복구 또는 홈 리다이렉트

### 중요

1. 무사용자 타임아웃과 세션 `abandoned/timeout` 처리
2. 음성 `place_order` 전 장바구니 동기화 보장
3. 추천 API 호출 debounce/cache
4. 카메라 실패 시 일반 주문 fallback

### 나중에 실제 운영 전 정리

1. 스탬프/주차/영수증/리뷰 기능의 실제 API 연동 여부 결정
2. 주문번호를 랜덤값이 아닌 서버 주문 정보로 표시
3. 로그 flush 유실 방지
4. 성별 unknown 추천 정책 정리
