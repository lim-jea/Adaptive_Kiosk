# 추천 시스템 현재 구조와 평가

## 1. 문서 목적

이 문서는 현재 백엔드에 구현된 추천 시스템이 실제로 어떤 계산 과정을 거쳐 동작하는지 정리한 문서다.

특히 아래를 구분해서 설명한다.

- 코드 기준의 실제 동작
- 추천 점수 계산 흐름
- 트렌드 가중치 반영 방식
- 추천 시스템 관점에서의 객관적 평가


## 2. 현재 추천 시스템의 전체 구조

현재 추천 시스템은 하나의 순수한 CF 모델이라기보다는, 아래 요소를 결합한 하이브리드 구조다.

- 상황 기반 추천
  - 성별, 연령대, 시간대에 따라 많이 주문된 메뉴 통계
- item-based 협업 필터링 신호
  - 장바구니 메뉴와 함께 주문된 메뉴의 공구매 관계
- 전역 인기 보정
  - 전체 상황 캐시에서 평균적으로 자주 등장하는 메뉴
- 네이버 트렌드 보정
  - 최근 3일~어제 기준 검색량 가중치

즉 현재의 `suggest` 추천은 아래 형태로 이해하는 것이 가장 정확하다.

- `상황 기반 추천 + item-based CF + 전역 인기 + 외부 트렌드 가중치`


## 3. 서비스 진입점

현재 프론트/백엔드에서 실제 사용하는 추천 API는 두 개다.

- `GET /api/v1/recommendations/situation`
  - 상황 기반 추천만 수행
- `POST /api/v1/recommendations/suggest`
  - 통합 추천 수행

운영상 메인 추천 경로는 `suggest`이고, `situation`은 fallback 성격이 강하다.


## 4. 서버 시작 시 준비 과정

서버 시작 시 추천 엔진은 배치처럼 동작한다.

### 4.1 추천 통계 배치

시작 시점에 CSV 기반 주문 로그를 읽는다.

- `data/kiosk_sessions.csv`
- `data/orders.csv`
- `data/order_items.csv`

그 다음 아래 두 종류의 통계를 메모리 캐시에 올린다.

- `mode_a`
  - 성별 × 연령대 × 시간대별 상위 메뉴 통계
- `mode_b`
  - 메뉴 간 공구매 통계

주의할 점:

- 코드 내부 이름은 아직 `mode_b`이지만,
- 현재 외부 API의 `Mode B` 추천 엔드포인트용이라기보다는
- `suggest` 내부의 item-based CF 신호로 쓰이고 있다.

### 4.2 메뉴 ID 매핑

DB에서 실제 판매 가능한 메뉴를 읽어 `menu_id -> menu_name` 매핑을 메모리에 저장한다.

이 매핑은 추천 결과를 프론트에 내려줄 때 사용된다.

### 4.3 트렌드 캐시 준비

네이버 트렌드 기능이 켜져 있으면:

- 오늘 날짜의 스냅샷 파일이 있으면 즉시 로드
- 없으면 백그라운드에서 최근 3일~어제 기준 트렌드 가중치를 계산

트렌드가 비활성화되어 있으면 추천은 `trend_weight = 1.0` 기준으로 동작한다.


## 5. 상황 기반 추천(`situation`) 계산 과정

`situation`은 현재 시간과 사용자 프로필만 보고 추천한다.

### 5.1 입력

- 성별 `M/F`
- 나이 또는 연령대
- 현재 시각

### 5.2 전처리

- 나이를 연령대로 변환
  - 예: `35 -> 30~39`
- 현재 시각을 시간대로 변환
  - `morning`, `lunch`, `afternoon`, `evening`, `night`

### 5.3 캐시 조회

배치에서 미리 계산해 둔 `mode_a` 캐시에서 아래 키로 조회한다.

- `gender:{gender},age:{age_group},period:{time_period}`

예:

- `gender:M,age:30~39,period:afternoon`

### 5.4 후보 점수

각 메뉴의 기본 점수는 그 상황에서의 `popularity`다.

- `popularity = 해당 상황에서 메뉴 주문 수 / 해당 상황 전체 아이템 수`

### 5.5 트렌드 보정

트렌드 기능이 켜져 있으면 메뉴별 트렌드 가중치를 곱한다.

- `final_score = popularity * trend_weight`

### 5.6 결과

`final_score` 기준으로 정렬한 상위 메뉴를 반환한다.


## 6. 통합 추천(`suggest`) 계산 과정

`suggest`는 현재 시스템의 핵심 추천 경로다.

이 과정은 “상황 기반 후보 + item-based CF + 전역 인기 + 트렌드 보정”의 조합이다.

### 6.1 입력

- 성별
- 나이
- 장바구니 메뉴 ID 목록
- 추천 개수
- 트렌드 포함 여부

### 6.2 사용자 컨텍스트 생성

- 나이를 연령대로 변환
- 현재 시간을 시간대로 변환

예:

- 성별 `M`
- 나이 `35`
- 연령대 `30~39`
- 현재 시간대 `afternoon`

### 6.3 상황 기반 프로필 캐시 조회

`mode_a` 캐시에서 현재 사용자 프로필의 추천 통계를 가져온다.

이 단계에서 현재 사용자와 비슷한 집단이 자주 고른 메뉴 목록을 얻는다.

### 6.4 기본 후보 생성

초기 후보 메뉴는 두 그룹의 합집합이다.

- 현재 프로필에서 상위 메뉴들
- 장바구니 메뉴와 함께 자주 주문된 메뉴들

즉 장바구니가 비어 있으면 프로필 상위 메뉴가 중심이 되고,
장바구니가 있으면 공구매 후보가 추가된다.

### 6.5 프로필 기반 점수

각 후보 메뉴는 먼저 아래 값을 가진다.

- `profile_popularity`
  - 현재 프로필 캐시 내에서의 인기
- `global_popularity`
  - 전체 `mode_a` 캐시들에서 평균적으로 얼마나 자주 등장하는지

기본 점수는 아래처럼 계산된다.

- `base_cf_score = 0.6 * profile_popularity + 0.4 * global_popularity`

엄밀히 말하면 이 값은 전통적인 CF 점수라기보다는
“상황 기반 인기 + 전역 인기 보정”에 가깝다.

### 6.6 장바구니 기반 item-based CF 점수

장바구니가 있으면 각 후보 메뉴에 대해 공구매 기반 점수를 계산한다.

원천 데이터는 배치에서 만든 `mode_b` 공구매 캐시다.

구체적으로는:

- 장바구니의 각 메뉴와 후보 메뉴 사이의 공구매 강도(`strength`)를 모은다.
- 그중 가장 강한 연결을 우선 반영한다.
- 여러 장바구니 메뉴와 동시에 연결되면 작은 보너스를 준다.

현재 구현식:

- `strongest_link = max(strengths)`
- `avg_link = average(strengths)`
- `coverage_bonus = min(0.03, 0.01 * (연결된 장바구니 메뉴 수 - 1))`
- `cart_cf_score = strongest_link * 0.75 + avg_link * 0.25 + coverage_bonus`

이 방식은 다음 의도를 가진다.

- 메뉴가 많아질수록 점수가 평균으로 희석되는 문제를 줄임
- 적어도 하나의 강한 공구매 신호가 있으면 후보가 살아남게 함
- 여러 메뉴와 동시에 연관되면 약하게 우대

### 6.7 통합 CF 점수

장바구니가 없으면:

- `cf_score = base_cf_score`

장바구니가 있으면:

- `cf_score = 0.35 * base_cf_score + 0.65 * cart_cf_score`

즉 장바구니가 존재할 때는 item-based CF를 더 우선하되,
상황 기반 추천이 완전히 사라지지 않도록 균형을 둔다.

### 6.8 트렌드 가중치 반영

트렌드가 켜져 있으면 각 메뉴에 대해 네이버 검색량 기반 가중치를 조회한다.

현재 최종식:

- `final_score = cf_score + (trend_score * 0.15)`

주의:

- 여기서 트렌드는 곱셈이 아니라 가산 방식으로 반영된다.
- `situation`에서는 `popularity * trend_weight`
- `suggest`에서는 `cf_score + trend * 0.15`

즉 두 경로의 트렌드 반영 방식은 서로 다르다.

### 6.9 장바구니 메뉴 제외

이미 장바구니에 들어 있는 메뉴는 추천 목록에서 제외한다.

따라서 `suggest`는 장바구니에 이미 담은 메뉴를 다시 추천하지 않는다.

### 6.10 최종 결과

`final_score` 내림차순으로 정렬한 후 상위 `top_n`을 반환한다.


## 7. 프론트와의 연결 방식

프론트는 현재 다음 흐름으로 추천을 사용한다.

### 7.1 기본 경로

- 나이가 있으면 `suggest` 호출
- 연령대만 있으면 `situation` 호출

### 7.2 fallback

`suggest` 실패 시 `situation`으로 fallback한다.

### 7.3 장바구니 반영

프론트는 장바구니에서 메뉴 ID들을 뽑아 `cart_items`로 `suggest`에 전달한다.

현재 특징:

- 같은 메뉴를 여러 개 담아도 하나의 menu_id로만 전달
- 수량은 현재 추천 점수에 직접 반영하지 않음


## 8. 객관적 평가

아래 평가는 “추천 시스템 이론”이 아니라 “현재 코드가 어떤 성격의 추천 시스템인지”를 기준으로 판단한 것이다.

### 8.1 상황 기반 추천(`situation`)의 타당성

평가: **타당함**

이유:

- 성별, 연령대, 시간대별 실제 주문 로그를 사용한다.
- 규칙 기반 하드코딩이 아니라 데이터 기반 빈도 통계다.
- 키오스크처럼 개인 사용자 이력이 적은 환경에서 cold-start 대응이 좋다.

한계:

- 개인화 수준은 낮다.
- 특정 사용자 취향보다 “비슷한 집단의 평균 행동”에 가깝다.

정리:

- `상황 기반 랭킹 추천`으로는 충분히 타당하다.
- 다만 이것만으로는 CF라고 부르기 어렵다.

### 8.2 통합 추천(`suggest`)의 타당성

평가: **부분적으로 타당함**

이유:

- 장바구니와 공구매 관계를 활용하므로 item-based CF 성격이 분명히 있다.
- 기존 상황 기반 추천과 공구매 신호를 섞는 방식은 실제 서비스에서 흔한 하이브리드 접근이다.
- 키오스크 환경에서는 사용자 장기 이력이 없기 때문에 user-based CF보다 현실적이다.

한계:

- 전통적인 CF 모델처럼 사용자-아이템 행렬을 분해하거나 유사도를 정교하게 학습하지는 않는다.
- `base_cf_score`는 사실상 CF라기보다 상황 인기 보정 점수다.
- 장바구니 수량, 순서, 옵션 조합은 현재 반영하지 않는다.
- 후보군이 여전히 `mode_a` 캐시에 많이 의존하므로 item-based CF만으로 완전히 재정렬되는 구조는 아니다.

정리:

- 현재 `suggest`는 “순수 CF”보다는 “상황 기반 추천에 item-based CF를 얹은 하이브리드 추천”으로 보는 것이 정확하다.
- 이 정의로 보면 충분히 타당하다.
- 하지만 “정통적인 CF 시스템”이라고 단정하는 것은 과장이다.

### 8.3 공구매 기반 점수의 타당성

평가: **타당함**

이유:

- 장바구니 추천에서 공구매(co-purchase)는 매우 일반적인 신호다.
- 특히 키오스크/커머스에서는 함께 주문되는 메뉴를 추천하는 것이 직관적이다.
- 장바구니가 늘어날 때 강한 연결을 살리는 현재 방식은 사용자 체감에도 맞다.

주의:

- 지금은 강한 연결을 우선하는 휴리스틱이다.
- 복잡한 유사도 모델은 아니므로 설명 가능성은 좋지만 정교함은 제한적이다.

### 8.4 전역 인기 보정의 타당성

평가: **타당함**

이유:

- 데이터가 적거나 특정 프로필 통계가 약할 때 추천 안정성을 높여준다.
- 극단적으로 희소한 프로필 때문에 이상한 메뉴가 튀는 것을 막는다.

주의:

- 전역 인기 비중이 너무 높으면 개인화가 약해질 수 있다.
- 현재는 장바구니가 있을 때 비중을 낮춰 둔 상태라 비교적 균형적이다.

### 8.5 트렌드 가중치 반영의 타당성

평가: **조건부 타당**

이유:

- 외부 검색량을 반영하면 계절성/이슈성 메뉴를 더 빨리 잡을 수 있다.
- 커피/음료처럼 날씨와 시즌 영향을 받는 카테고리에서는 실무적으로 의미가 있다.

한계:

- 검색량은 실제 구매 전환과 다를 수 있다.
- 메뉴명과 검색어가 정확히 일치하지 않으면 잡음이 생길 수 있다.
- `situation`과 `suggest`에서 트렌드 반영 방식이 다르므로 일관성은 다소 떨어진다.

정리:

- 보조 신호로는 타당하다.
- 핵심 추천 로직보다 강하게 쓰면 오히려 왜곡될 수 있다.


## 9. 최종 종합 평가

현재 추천 시스템은 아래처럼 평가할 수 있다.

- 상황 기반 추천: **타당**
- 장바구니 기반 item-based CF: **타당**
- 전체 통합 추천: **실무형 하이브리드 추천으로 타당**
- 순수 CF 시스템 여부: **아님**

즉 현재 시스템을 가장 정확하게 부르면 다음과 같다.

- `상황 기반 랭킹 + item-based 공구매 추천 + 트렌드 보정이 결합된 하이브리드 추천 시스템`

이 표현이 현재 구현을 가장 객관적으로 설명한다.


## 10. 현재 구조의 장점

- 키오스크 환경에 잘 맞는다.
- 개별 사용자 장기 이력이 없어도 동작한다.
- cold-start에 강하다.
- 공구매 기반 추천이 있어 장바구니 변화에 반응한다.
- 트렌드 보정을 켜고 끌 수 있다.
- 배치 계산 후 메모리 캐시를 사용하므로 추론 시 빠르다.


## 11. 현재 구조의 한계

- 엄밀한 의미의 CF 모델은 아니다.
- 장바구니 수량이 추천 점수에 반영되지 않는다.
- 옵션 조합과 메뉴 조합의 관계는 반영하지 않는다.
- 트렌드 반영 방식이 경로별로 일관적이지 않다.
- 내부 명칭(`mode_b`)이 현재 역할과 완전히 맞지는 않는다.
- 배치 데이터가 CSV 기반이라 실시간 주문 누적 반영에는 한계가 있다.


## 12. 개선 우선순위 제안

현재 구조를 크게 흔들지 않는 선에서의 우선순위는 아래가 적절하다.

1. `mode_b` 내부 명칭을 `item_cf` 또는 `copurchase_cache` 쪽으로 정리
2. 장바구니 수량을 `cart_cf_score`에 반영
3. 트렌드 반영식을 `situation`과 `suggest`에서 일관되게 정리
4. CSV 대신 실제 주문 DB를 기준으로 배치 통계 생성
5. 필요 시 장기적으로는 사용자 세션/주문 이력을 이용한 더 정교한 CF 모델 도입


## 13. 한 줄 결론

현재 추천 시스템은 “정통 CF”는 아니지만, 키오스크 환경에서 충분히 타당한 하이브리드 추천 시스템이며, 특히 `suggest`는 상황 기반 추천 위에 장바구니 item-based CF를 얹은 실무형 구조로 보는 것이 가장 정확하다.
